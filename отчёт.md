## 2. Поднятые сервисы — и почему именно они

Проверил через `docker ps`: работают `lakehouse-minio`, `lakehouse-pg`, `lakekeeper`, `trino`.

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO (образ `pgsty/silo`) | S3-совместимое объектное хранилище: сюда физически падают parquet-файлы | Данные лежат отдельно от вычислений и доступны любому движку по S3 API; при переезде в облако заменяется на настоящий S3 без изменения кода. Официальные образы MinIO стали платными, поэтому взял свободный форк Silo — те же порты и переменные окружения. |
| PostgreSQL 17 (порт 55432) | БД, где Lakekeeper хранит метаданные каталога | Без неё Lakekeeper не работает; Postgres — открытый, надёжный и транзакционный, поэтому метаданные каталога не теряются. Порт 55432 взял, чтобы не конфликтовать с локальным Postgres на 5432. |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Реализует стандартный REST-протокол Iceberg, поэтому и Trino, и Spark подключаются к нему одинаково. Это один лёгкий контейнер, а Hive Metastore был бы тяжелее и капризнее. |
| Trino 476 (порт 18080) | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | Есть встроенный коннектор `tpch`, который сам генерирует данные, и Iceberg-коннектор с откатом и schema evolution. Запросы считаются за доли секунды на sf1. Порт 18080 взял, чтобы не конфликтовать с локальными сервисами на 8080. |
| (BI: Superset / Metabase) | не поднимал | В п. 6.2 нужен один инструмент — я выбрал Spark как движок, а не BI. |

### Скрипты, которыми поднимал стек

Полные скрипты лежат в `infra/`: `start-stack.ps1`, `restart-stack.ps1`, `create-warehouse.json`, `catalog/*.properties`. Ключевые команды из `start-stack.ps1`:

```powershell

docker run -d --name lakehouse-minio -p 9000:9000 -p 9001:9001 `
  -e MINIO_ROOT_USER=minioadmin -e MINIO_ROOT_PASSWORD=minioadmin `

# bucket warehouse для данных
docker run --rm --entrypoint /bin/sh --add-host host.docker.internal:host-gateway `
  pgsty/mc:latest -c "mc alias set m http://host.docker.internal:9000 minioadmin minioadmin && mc mb --ignore-existing m/warehouse"

# PostgreSQL — метаданные Lakekeeper, порт 55432
docker run -d --name lakehouse-pg -e POSTGRES_PASSWORD=postgres -p 55432:5432 `
  -v pg-data:/var/lib/postgresql/data postgres:17

# Lakekeeper — сначала миграции БД (порт 55432), затем сервис
docker run --rm --add-host host.docker.internal:host-gateway `
  -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' `

  -e 'LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@host.docker.internal:55432/postgres' `
  quay.io/lakekeeper/catalog:latest-main migrate
docker run -d --name lakekeeper --add-host host.docker.internal:host-gateway `
  (те же переменные окружения) -p 8181:8181 `
  quay.io/lakekeeper/catalog:latest-main serve

# warehouse demo
curl.exe -s -X POST http://localhost:8181/management/v1/warehouse `
  -H "Content-Type: application/json" -d '@create-warehouse.json'

# Trino — каталоги читает из папки catalog/, порт 18080

  -v "${PWD}/catalog:/etc/trino/catalog" trinodb/trino:476
```

## 3. Разбор запроса — какие данные нужны

Q16 использует 3 таблицы TPC-H. Из `part` и `partsupp` беру только нужные колонки, из `supplier` — только `comment` для подзапроса исключения.

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| `part` | `partkey`, `brand`, `type`, `size` | фильтры `brand <> 'Brand#45'`, `type NOT LIKE 'MEDIUM POLISHED'`, `size IN (49,14,23,45,19,3,36,9)`; `partkey` — джойн с `partsupp`; `brand`, `type`, `size` — группировка и вывод |
| `partsupp` | `partkey`, `suppkey` | `partkey` — джойн с `part`; `suppkey` — джойн с `supplier` и агрегат `count(DISTINCT suppkey)` |
| `supplier` | `suppkey`, `comment` | подзапрос `suppkey NOT IN (...)` по `comment LIKE '%Customer%Complaints%'` |

## 4. Медальон — решения по каждому слою

Вес считал по системным таблицам `$files`, кодек проверял через `$properties`. Во всех слоях по одному файлу на таблицу (на sf1 это нормально).

### Bronze (сырой)

Данные лежат как в источнике — без фильтров и без изменения значений.

| Таблица | Колонки (что оставил) | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|
| `bronze.part` | `partkey`, `brand`, `type`, `size`, `comment` | 200 000 | ~2,5 | PARQUET | ZSTD | нет | Parquet читает только нужные колонки, его понимают и Trino, и Spark. ZSTD сжимает как GZIP, но пишется быстрее. Таблица маленькая — партиции не нужны. |
| `bronze.partsupp` | `partkey`, `suppkey` | 800 000 | ~3,5 | PARQUET | ZSTD | нет | Самая крупная таблица Bronze. 3,5 МБ — мало для партиций: тысячи мелких файлов только замедлят планирование. |
| `bronze.supplier` | `suppkey`, `comment` | 10 000 | ~1,0 | PARQUET | ZSTD | нет | Маленький справочник; нужен только ради `comment` для подзапроса исключения. |

### Silver (очищенный)

Что делает Silver (`sql/04_silver.sql`):

- **Нормализация.** `brand` и `type` привожу к `upper(trim(...))`, чтобы фильтры Q16 не зависели от регистра и пробелов.
- **Очистка.** Убираю строки без ключей, без бренда, без размера; дубли по `(partkey, suppkey)` оставляю в одном экземпляре. В TPC-H таких нет, но правила оставлены на будущее.
- **Обогащение.** У поставщика появляется булев флаг `has_complaint` — считается один раз на весь Silver. Это упрощает Gold: вместо подзапроса `suppkey NOT IN (...)` — `has_complaint = false`.

| Таблица | Колонки (что оставил) | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|
| `silver.part` | `partkey`, `brand`, `type`, `size` | 200 000 | ~2,2 | PARQUET | ZSTD | нет | Из Bronze-таблицы убрал `comment` — Q16 он не нужен, а без него таблица чуть компактнее. |
| `silver.partsupp` | `partkey`, `suppkey` | 800 000 | ~3,0 | PARQUET | ZSTD | нет | Дубли и пустые ключи убраны, остальное — как в Bronze. |
| `silver.supplier` | `suppkey`, `comment`, `has_complaint` | 10 000 | ~1,1 | PARQUET | ZSTD | нет | Добавлен флаг `has_complaint`, чтобы Gold не содержал подзапрос. |

### Gold (витрина)

| Таблица | Колонки | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|
| `gold.parts_supplier_count` | `brand`, `type`, `size`, `supplier_cnt` | порядка нескольких сотен | меньше 0,1 | PARQUET | ZSTD | нет | Это готовый ответ на Q16: агрегат по бренду/типу/размеру. Таблица крошечная, поэтому формат и кодек выбраны «как везде», чтобы не плодить варианты. Проверка против Q16 напрямую на `tpch.sf1` даёт 0 расхождений. |

## 5. Тесты производительности

### Как мерил

Взял те же три таблицы Bronze (sf1) и записал их в 8 вариантах: формат Parquet и ORC × кодеки NONE, SNAPPY, GZIP, ZSTD. Для каждого варианта измерил:

- размер и число файлов — по `$files`;
- время записи — `Measure-Command` вокруг записи трёх таблиц;
- время Q16 — 3 прогона, время из `system.runtime.queries`; в отчёте — медиана.

Trino и MinIO у меня на одном ноутбуке, диск быстрый, а разница во времени запросов небольшая (десятки–сотни миллисекунд) и местами похожа на шум. Поэтому по скорости чтения делаю только осторожные выводы.

### Результаты (sf1, Bronze)

Цифры с моего прогона (`logs/format-matrix.log`). На другом железе будут слегка отличаться, но порядок величин и выводы сохранятся.

| Формат | Кодек | Размер, МБ | Файлов | Меньше, чем NONE | Время записи, с | Q16, мс (медиана) |
|---|---|---|---|---|---|---|
| Parquet | NONE | ~7,0 | 3 | — | ~1,3 | ~260 |
| Parquet | SNAPPY | ~4,0 | 3 | −43 % | ~1,4 | ~300 |
| Parquet | GZIP | ~2,8 | 3 | −60 % | ~3,0 | ~330 |
| Parquet | ZSTD | ~2,8 | 3 | −60 % | ~1,7 | ~280 |
| ORC | NONE | ~7,1 | 3 | — | ~1,4 | ~290 |
| ORC | SNAPPY | ~4,2 | 3 | −41 % | ~1,5 | ~310 |
| ORC | GZIP (zlib) | ~2,9 | 3 | −59 % | ~2,0 | ~300 |
| ORC | ZSTD | ~3,0 | 3 | −58 % | ~1,3 | ~290 |

Отдельно в форме из задания (пересоздание Bronze только с GZIP и ZSTD, Q16 три раза):

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему) |
|---|---|---|---|
| GZIP | ~320 мс | ~2,8 | Размер почти как у ZSTD, но запись в ~2 раза медленнее, а запрос не быстрее. |
| ZSTD | ~280 мс | ~2,8 | Лучше: размер тот же, запись в ~2 раза быстрее, запрос не медленнее. |

### Ответы на вопросы

1. **Размер.** Сильнее всего сжимают GZIP и ZSTD: Parquet-файлы примерно на 60 % меньше, чем без сжатия. SNAPPY слабее — около 43 %. При одинаковом кодеке Parquet компактнее ORC на 1–10 %.
2. **Запись.** GZIP в Parquet писался примерно в 2 раза дольше, чем NONE (~3 с против ~1,3 с). Зато экономия места 60 %; для данных, которые пишутся один раз и читаются много, это оправдано.
3. **Чтение.** Быстрее всего шёл запрос на Parquet NONE, потому что ничего не надо распаковывать, а диск локальный. Но на удалённом хранилище лишние 4 МБ у NONE замедлили бы запрос. ZSTD почти не отстаёт при вдвое меньшем размере — хороший компромисс.
4. **Компромисс.** SNAPPY — для «горячих» данных, где важнее скорость записи. ZSTD — по умолчанию: сжимает как GZIP, работает почти как SNAPPY. GZIP — для архивов, которые читают редко.
5. **Метаданные и кэш.** Объём метаданных Iceberg отдельно не мерил, но по `$files` видно, что файлов мало, и манифесты весят килобайты. Повторные прогоны обычно быстрее первых: у Parquet GZIP первый прогон может быть 400+ мс, а второй и третий — около 300 мс. Это похоже на кэш, поэтому в отчёте медиана из трёх прогонов, а не лучшее время.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Данных становится слишком много для одной БД, и они бывают разные. В lakehouse они лежат в дешёвом объектном хранилище в открытых форматах (Parquet + Iceberg), а вычисления отдельно. Одну и ту же таблицу читают и Trino, и Spark, без копирования. По сравнению с простой кучей файлов (data lake) Iceberg добавляет транзакции, схему, снапшоты и откат. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | Добавил колонку `supply_share` через `ALTER TABLE ... ADD COLUMN`. Файлы не переписывались — поменялись только метаданные. У всех старых строк в новой колонке `NULL`. Потом переименовал в `line_share` и удалил — схема вернулась как была. |
| Пример скрипта восстановления данных из снапшота (time travel) | Ниже — из `scripts/evolve-and-timetravel.ps1`. В Silver-таблице `partsupp` я «случайно» удалил половину строк (`DELETE ... WHERE suppkey % 2 = 1`), число строк упало. Старый снапшот остался целым, через `FOR VERSION AS OF` в нём видно исходное число. `rollback_to_snapshot` вернул таблицу. |

```powershell
$T = "lakekeeper.silver.partsupp"
$good = (docker exec trino trino --output-format CSV_UNQUOTED --execute `
  "SELECT snapshot_id FROM lakekeeper.silver.`"partsupp`$snapshots`" ORDER BY committed_at DESC LIMIT 1")[-1]
docker exec trino trino --output-format ALIGNED --execute "SELECT count(*) FROM $T"                          # исходное число
docker exec trino trino --output-format ALIGNED --execute "DELETE FROM $T WHERE suppkey % 2 = 1"             # авария
docker exec trino trino --output-format ALIGNED --execute "SELECT count(*) FROM $T"                          # стало меньше
docker exec trino trino --output-format ALIGNED --execute "SELECT count(*) FROM $T FOR VERSION AS OF $good"  # старое число цело
docker exec trino trino --output-format ALIGNED --execute "ALTER TABLE $T EXECUTE rollback_to_snapshot($good)"
docker exec trino trino --output-format ALIGNED --execute "SELECT count(*) FROM $T"                          # восстановлено
```

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| Apache Spark 3.5.1 в Docker | Spark читает Iceberg через тот же Lakekeeper и те же файлы в MinIO, ничего не копируя. Так видно главную идею lakehouse: данные, записанные Trino, читает другой движок. Doris и StarRocks сложнее — им нужно либо загружать данные, либо настраивать внешние каталоги. Spark ещё и масштабируется на кластер. |

Скрипты: `scripts/spark-bronze.ps1` и `spark/bronze_demo.py` (запуск `apache/spark:3.5.1` с пакетами `iceberg-spark-runtime-3.5_2.12:1.5.2` и `iceberg-aws-bundle:1.5.2`, каталог `lakekeeper` настроен как REST на `http://host.docker.internal:8181/catalog`, S3 на `http://host.docker.internal:9000`). Полный вывод — `logs/spark-bronze.log`.

Что сделал и увидел на Bronze:

1. Подключил Spark к тому же каталогу, что и Trino.
2. `SHOW TABLES IN lakekeeper.bronze` показал три таблицы, которые создал Trino: `part`, `partsupp`, `supplier`.
3. Число строк в Spark то же, что в Trino: 200 000 / 800 000 / 10 000.
4. Q16 на Bronze в Spark вернул те же строки, что и Gold.
5. Время Q16 в Spark — по строке на прогон; первый прогон заметно дольше из-за прогрева, следующие — в районе 1 с. У Trino на тех же данных — доли секунды, потому что Trino — интерактивный движок с быстрым стартом.

## 7. Выводы

Медальон получился трёхшаговым. Bronze хранит данные как пришли, Silver нормализует и обогащает (флаг `has_complaint`, `upper(trim())`), а Gold отдаёт готовый ответ Q16 — и он совпал с запросом напрямую на `tpch.sf1`. Бенчмарк показал, что любое сжатие сильно экономит место (SNAPPY — на ~43 %, GZIP и ZSTD — на ~60 %), но лучший баланс у ZSTD: размер как у GZIP, запись в 2 раза быстрее, чтение почти как без сжатия. На моих данных Parquet оказался компактнее ORC, поэтому для всех слоёв выбрал Parquet + ZSTD. Партиции на sf1 не нужны: таблицы маленькие, и вышли бы тысячи мелких файлов. Iceberg позволил добавить и убрать колонку без перезаписи данных, а после случайного `DELETE` вернуть таблицу из снапшота. Чтение тех же таблиц из Trino и Spark подтвердило, что данные в lakehouse не привязаны к одному движку.
